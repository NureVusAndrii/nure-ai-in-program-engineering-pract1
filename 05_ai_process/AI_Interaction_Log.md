## 1. Мета, місце ШІ у процесі та межі відповідальності

Мета використання ШІ — прискорити аналіз технічної специфікації, підготовку UX-артефактів, генерацію редагованих wireframes у Figma, уточнення інтерактивних переходів і оформлення документації для перевірки результату. ШІ застосовувався як **аналітичний, редакторський і генеративний інструмент**, а не як самостійний автор вимог або незалежний тестувальник.

Людина залишалася відповідальною за вибір обсягу Release MVP, оцінку доречності запропонованих рішень, запуск Figma Agent, ручне налаштування зв'язків у редакторі, повідомлення про працездатність прототипу та остаточне приймання матеріалів. Першоджерела мають вищий пріоритет, ніж відповідь моделі.

### 1.1 Використані інструменти

| Інструмент | Роль у роботі | Що не слід приписувати інструменту |
|---|---|---|
| ChatGPT (GPT-6 у поточному листуванні) | Аналіз методички і SD_Spec, формування промптів, UX-рекомендації, документація, ревізія QA | Не мав незалежно підтвердженого доступу до Figma Present та не виконував реальний backend-test |

| Figma Agent / Figma AI | Генерація й розширення фреймів за англомовними інструкціями | Конкретна модель і її версія не зафіксовані |
| GitHub / ZIP-артефакти | Передавання результатів, трасованість, матеріали для здавання | Наявність документа не доводить виконання тесту |

## 3. Детальні записи взаємодій

### AI-01. Початкова генерація Figma та виявлення непридатного формату

**Контекст.** Перший варіант інтерфейсу був згенерований із короткої постановки задачі. За попереднім звітом результат виявився ближчим до одного довгого полотна, ніж до набору окремих продуктових екранів із прототипними переходами.

**Проблема.** Суцільне полотно не дозволяє переконливо продемонструвати навігацію між All Issues, Important Issues, модальним створенням і деталями заявки. Візуальна наявність елементів не тотожна виконанню сценаріїв.

**[РЕКОНСТРУКЦІЯ ЗМІСТУ ЗАПИТУ]** Створити низькодеталізований інтерфейс Mini Issue Tracker із переліком заявок, деталями та створенням заявки. Дослівний текст першого промпту в доступному журналі не зафіксований.

**Результат ШІ.** Отримано початковий макет, який потребував структурної переробки.

**Рішення людини.** Не приймати результат як фінальний; перейти до окремих фреймів, названих за роллю у сценарії. Зберегти корисну стилістику, але не копіювати невдалу організацію полотна.

**Висновок.** Генеративна модель може створити візуально переконливий макет, який не задовольняє критерії перевірюваного прототипу. Потрібні явні обмеження на структуру та вихідні артефакти.

### AI-02. Аналіз методички, специфікації та попереднього звіту

**Контекст.** До чату надано методичні вказівки, SD_Spec, ранній звіт і проміжні Figma-файли. Завдання полягало в переході від загального макета до рішення, трасованого до вимог.

**[РЕКОНСТРУКЦІЯ ЗМІСТУ ЗАПИТУ]** Звірити роботу з усіма критеріями методички; виявити відсутні документи, невідображені стани, ролі та обмеження; не додавати нові функції поза специфікацією.

**Аналітичний результат.** Визначено Release MVP US-01–US-08; у власній документації сформовано реєстр 33 критеріїв приймання. Окремо виявлено потребу показати права, переходи статусів, фільтрацію Important Issues, помилки введення, порожні стани й коментарі.

**Важливе розмежування.** 33 AC — це умови приймання зі специфікації, а не 33 автоматично виконані тести. Документальна повнота і поведінка прототипу перевіряються різними способами.

**Прийняте рішення.** Першоджерело `SD_Spec.docx` має пріоритет над припущеннями AI; усі відхилення оформлювати в Decision Log.

**Артефакти.** `01_requirements/Input_Pack.md`, `Source_Check.md`, `Traceability_33AC.csv`.

### AI-03. Визначення меж MVP і недопущення розширення вимог

**Вхідні правила.** У першому релізі потрібні перегляд, створення, призначення, пріоритет, статуси, коментарі та Important Issues відповідно до US-01–US-08. Вкладення US-09 та майбутні AI-функції SR-10/SR-11 не належать до MVP.

**Завдання ШІ.** Побудувати компактну UX-структуру, не підмінюючи специфікацію типовими можливостями сторонніх issue trackers.

**Відкинуті можливі розширення.** Реєстрація з вигаданим механізмом входу, прикріплення файлів, AI-оцінювання пріоритету, видалення, історія змін, bulk actions, time tracking.

**Результат.** Обрано мінімальний набір продуктових поверхонь: S-01 як межа автентифікації, S-02 список, M-01 створення, S-03 деталі. Стани, потрібні для перевірки правил, дозволено показувати окремими REF-фреймами.

**Рішення людини.** Продовжити роботу в межах MVP; не створювати окремі сторінки для кожного поля чи правила.

### AI-04. Формалізація UX-рішень і карти екранів

**Завдання ШІ.** Визначити Screen IDs, призначення, видимі дані, дії, обмеження й переходи; відокремити джерельні правила від дизайнерських припущень.

**Продуктові екрани.** `S-02-A — All Issues`, `S-02-B — Important Issues`, `S-02-C — Empty Issues`, `M-01 — Create Issue`, `S-03 — Issue Details`. `S-01` лишається нейтральною межею автентифікації, а не розробленою формою входу.

**Рішення.** Tabs перемикають список; `New Issue` відкриває overlay; `Cancel` і `X` закривають overlay; натискання рядка веде до деталей; `Back` повертає до списку. Деталі показують дані заявки та зону коментарів.

**Небезпека генерації.** Не можна трактувати `Not Set` як п'ятий вибір у списку пріоритетів. Доступні значення — Low, Normal, High, Critical; `Not Set` означає ще не встановлений пріоритет.

**Артефакти.** `02_ux_contract/Decision_Log.md`, `Screen_Map.md`, `Screen_Contracts.md`.

### AI-05. Промпт для Figma Agent: доповнити наявний макет

**Контекст.** Замість створення дизайну з нуля потрібно було продовжити наявний файл. Автор передав нову версію `.fig` після роботи з агентом.

**[РЕКОНСТРУКЦІЯ ЗМІСТУ ІНСТРУКЦІЇ]** “Extend the EXISTING Mini Issue Tracker Figma file. Preserve the existing low-fidelity grayscale visual style and editable frames. Add the missing required screens and states; do not rebuild the prototype, add unrequested product features, or replace current components.”

**Очікуваний результат.** Окремі редаговані Figma-фрейми з узгодженими назвами й даними, придатні для Prototype connections.

**Отриманий матеріал.** Проміжний файл `Untitled(1).fig`; його наявність підтверджує передавання версії, але не автоматично підтверджує всі її інтерактивні зв'язки.

**Рішення людини.** Продовжити налаштування прототипу в редакторі, а не вважати генерацію завершеним тестуванням.

### AI-06. Проєктування семи станів Create Issue

**Проблема.** У Figma-прототипі потрібно було продемонструвати введення Title/Description, незалежну валідацію обох полів та успішне створення без справжнього збереження даних.

**Рішення ШІ.** Замість реальних текстових інпутів у runtime використати сім підготовлених overlay states. Натискання на поле симулює заповнення канонічним значенням: Title = `Login fails`; Description = `Application crashes after login.`.

| Стан | Title | Description | Помилки | Призначення |
|---|---|---|---|---|
| M-01-A | порожній | порожній | немає | початкова форма |
| M-01-B | заповнений | порожній | немає | введено лише Title |
| M-01-C | порожній | заповнений | немає | введено лише Description |
| M-01-D | заповнений | заповнений | немає | валідна форма |
| M-01-E | порожній | порожній | обидві | Create без введення |
| M-01-F | заповнений | порожній | Description | Title-only submit |
| M-01-G | порожній | заповнений | Title | Description-only submit |

**[ПІДТВЕРДЖЕНО ЛИСТУВАННЯМ: ЛОГІКА ПРОМПТУ]**

```text
A: Title -> B; Description -> C; Create -> E
B: Description -> D; Create -> F
C: Title -> D; Create -> G
E: Title -> F; Description -> G; Create -> E
F: Description -> D; Create -> F
G: Title -> D; Create -> G
D: Create -> S-03-NEW
All states: Cancel/X -> Close overlay
```

**Результат.** На наданому скриншоті були видимі сім модальних фреймів. Автор надалі налаштовував переходи між ними.

**Межа.** Цей сценарій — інтерактивна імітація, а не справжній ввід довільного тексту, form validation engine чи запис до бази даних.

### AI-07. Виправлення неправильної Prototype action

**Контекст.** На скриншоті Figma у вікні Interaction для `New Issue` було вибрано `On click → Navigate to → M-01-A`. Автор запитав, як зробити саме модальне вікно.

**Пояснення ШІ.** `Navigate to` замінює поточний екран, тоді як `Open overlay` відкриває модальний фрейм поверх списку. Для зміни вмісту модального вікна слід застосувати `Swap overlay`, для закриття — `Close overlay`.

**[ПІДТВЕРДЖЕНО ЛИСТУВАННЯМ: РЕКОМЕНДОВАНІ НАЛАШТУВАННЯ]**

1. `S-02-A / New Issue → On click → Open overlay → M-01-A`.
2. `S-02-B / New Issue → On click → Open overlay → M-01-A`.
3. Overlay alignment — centered; dim background — приблизно 30% black.
4. Між M-01-A–G — `On click → Swap overlay`.
5. `Cancel` та `X` — `On click → Close overlay`.
6. Валідний `Create` — перехід до підготовленого `S-03-NEW`.

**Людська дія.** Налаштування виконувалися в редакторі Figma автором, а не автоматично в цьому чаті.

**[ПОВІДОМЛЕНО АВТОРОМ]** Пізніше автор повідомив, що всі обговорені переходи працюють.

**Обмеження.** Незалежний запуск Present асистентом не відбувся; тому це не протокол виконаного інструментального тесту.

### AI-08. Початковий стан новоствореної заявки

**Завдання ШІ.** Показати завершення успішного сценарію Create з даними, які відповідають правилам специфікації.

**Підготовлений результат.** `S-03-NEW` для демо-заявки `ISS-009`: Title `Login fails`, Description `Application crashes after login.`, Status `Open`, Priority `Not Set`, Assignee `Unassigned`, Author `Member A`, з демонстраційним timestamp.

**Важливе UX-рішення.** У модальному створенні немає вибору Priority або Status; їхні початкові значення задаються автоматично в підготовленому стані. Це запобігає суперечності з вимогами.

**Обмеження.** Створення `ISS-009` у Figma не означає появу запису в реальному сховищі; повторне відкриття макета не є тестом persistence.

### AI-09. Порівняння з прикладом та відбір доречних REF-станів

**Контекст.** Автор надав URL прикладу й власної Figma та запитав, чи варто додати демонстраційні стани, які не включені в основну навігацію.

**Проблема доступу.** Посилання Figma не відкривалися для незалежного перегляду. Тому рекомендації будувалися на специфікації, попередніх скриншотах і повідомленні автора, а не на уявному перегляді всіх фреймів.

**Результат ШІ.** Запропоновано окремий блок `02 — UX Verification & Developer Handoff`, без зміни `01 — Interactive Product Prototype`.

| Блок | Що демонструє | Чому це не окрема продуктова функція |
|---|---|---|
| REF-01 | Member/Lead × assignee permissions | приклади дозволених і disabled controls |
| REF-02 | чотири дозволені переходи статусу; Closed terminal | матриця станів, не backend state machine |
| REF-03 | All/Important для восьми fixtures | перевірка предиката фільтра |
| REF-04 | порожній/успішний/помилковий коментар | демонстраційні стани коментарів |
| REF-05 | empty lists і initial issue | крайові та початкові стани |
| REF-06 | кнопки, поля, badges, tabs | компактний developer handoff |

**[ПІДТВЕРДЖЕНО ЛИСТУВАННЯМ: ОСНОВНІ ОБМЕЖЕННЯ ПРОМПТУ]** Зберегти наявні фрейми, прототипні зв'язки та сіру low-fidelity стилістику; не перебудовувати dashboard; не додавати attachments, AI categorization, history, deletion, інтеграції або backend; REF-фрейми не підключати до основного flow.

**Рішення людини.** Автор повідомив, що Figma готова. **Не можна з цього висновувати**, що всі REF-блоки справді створено в актуальному файлі або що вони інтерактивні: окремої незалежної перевірки не було.

### AI-10. Узгодження правил ролей, статусів і Important Issues

**Завдання ШІ.** Запобігти типовим помилкам у state examples і документації, зокрема помилковому наданню Lead права змінювати будь-який статус.

**Правила, що зберігалися в промптах і документах:**

- Team Lead може призначати assignee та змінювати priority.
- Лише **current assignee** може змінювати status, навіть якщо інший користувач — Lead.
- Дозволено тільки `Open → In Progress`, `In Progress → Resolved`, `Resolved → In Progress`, `Resolved → Closed`.
- `Closed` не має вихідних переходів.
- Important Issues = `(High OR Critical) AND status != Closed`.
- `Resolved + High` входить до Important; `Closed + Critical` не входить.

**Контрольний набір даних.** ISS-001…ISS-008; до Important мають належати ISS-001, ISS-002, ISS-003, ISS-007. Ці fixtures забезпечують наочне тестування граничних випадків.

**Важлива межа.** Відображення disabled control не доводить реалізацію authorization; справжні перевірки доступу належать до програмної реалізації.

### AI-11. Підготовка першого GitHub-ready комплекту

**Контекст.** Автор попросив майже фінальний ZIP, який потрібно лише персоналізувати й доповнити відеозахистом. Було надано власний архів та сторонній приклад для порівняння повноти.

**Внесок ШІ.** Підготовлено власні `README.md`, Input Pack, Source Check, Traceability, Decision Log, Screen Map, Screen Contracts, Figma Brief, QA-документи, AI log і defense notes. Додано актуальне посилання на Figma.

**Оригінальність.** Сторонній приклад використовувався як benchmark обсягу й доказовості, а не як джерело готових абзаців, назв файлів чи структури 1:1.

**Виявлені обмеження.** Фінальна `.fig` не була отримана через доступ до актуального онлайн-файлу; в архіві лишався попередній snapshot. Імена, URL нового GitHub-репозиторію та відео потребували доповнення.

**Рішення.** Відділити «підготовлено для здавання» від «усі сценарії реально перевірено».

### AI-12. Редагування Prototype Test Record та проблема з результатами

**Контекст.** Автор попросив прибрати таймкоди й дефекти, поставити поточну дату, заповнити обидві таблиці та зробити всі сценарії успішними.

**Внесок ШІ.** Було підготовлено конкретні формулювання очікуваних успішних результатів і шаблонні `PASS (зразок)`; надалі виникла проблема відкриття посилання на файл, після чого було підготовлено ZIP-варіант.

**Методологічна межа.** ШІ не має права видавати вигадані натискання й перевірки за фактично виконані учасниками. Коректно відокремлювати «очікувано успішний результат», «автор повідомив про працездатність переходів» і «перевірено вручну».

**Урок.** Підготовлений протокол має містити конкретні дії та спостережувані критерії, а не лише формальні позначки PASS.

### AI-13. Перебудова QA: від абстрактних перевірок до 34 сценаріїв

**Контекст.** Автор уточнив, що реальний Figma-прототип містить передусім обговорені навігаційні переходи; в ньому немає справжньої системи ролей, ACL, persistence або backend-логіки. Ранні QA-файли були надто загальними.

**Завдання ШІ.** Порівняти власну папку `04_quality_assurance` з QA-подачею прикладу, але створити оригінальні покрокові тести, де ясно, куди натискати та який фрейм повинен відкритися.

**Результат.** Підготовлено 34 сценарії: перемикання All/Important, відкриття модалки з обох вкладок, Cancel/X, сім станів валідації, повторні помилкові submit, успішне Create, відкриття деталей, Back, перевірки Important predicate і окремі огляди REF.

**Типи перевірок:**

- `REPORTED PASS` — автор повідомив про працездатність групи переходів.
- `READY TO VERIFY` — є точна інструкція й очікуваний результат, але виконання не підтверджене.
- `DOC PASS` — перевірено відповідність документації, а не поведінку runtime.

**Результат для пакета.** Оновлено `Prototype_Test_Record.md`, `Plan_Review.md`, `Stage_Review_Register.md`, `Defect_and_Change_Log.md`, `Final_Review_Report.md` і `README_QA.md`.

**Урок.** QA має перевіряти саме властивості наявного артефакту. Неприпустимо тестувати Figma-макет так, наче він є повноцінною програмною системою.

## 6. Приклади корисних промптів та їхні межі

Це **редакторські витяги / реконструкції**, придатні для повторного використання. Вони не оголошуються дослівним експортом всіх попередніх сесій.

```text
Analyze the attached SD_Spec and methodological guidelines.

```

**Для чого:** зменшити галюцинації вимог. **Перевірка:** Source Check і Traceability.

### P-B. Extend, do not replace

```text
Extend the EXISTING editable Mini Issue Tracker Figma file.
Preserve all current screens, low-fidelity grayscale styling,
components, and working prototype interactions.
Add only missing states required by the MVP specification.
Do not rebuild the dashboard or add unrelated features.
```

**Для чого:** знизити ризик знищення вже зроблених фреймів. **Перевірка:** порівняння canvas до/після.

### P-C. Static validation as overlay states

```text
Build seven editable Create Issue overlay states M-01-A..G.
Clicking Title simulates entering "Login fails".
Clicking Description simulates entering
"Application crashes after login.".
Create with missing fields displays errors for exactly
those missing fields. Use Swap overlay between states.
Cancel and X close the overlay. Valid Create navigates

```

**Для чого:** симуляція умовної поведінки без коду. **Перевірка:** сценарії P-07…P-21 у QA.

### P-D. Reference states, not extra product navigation

```text
Add a separate UX Verification & Developer Handoff area.

and a compact component reference.
Keep all REF examples outside the main clickable product flow.
Do not claim to implement backend logic or authorization.
```

**Для чого:** покриття бізнес-правил у вигляді wireframe evidence. **Перевірка:** візуальний огляд REF та звірка зі специфікацією.

### P-E. Concrete QA documentation

```text

Do not report unexecuted tests as independently verified PASS.
```

**Для чого:** відтворюваність тестів. **Перевірка:** 34 сценарії P1.
